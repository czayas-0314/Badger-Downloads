# Support and feedback

[Report a bug](https://github.com/czayas-0314/Badger-Downloads/issues/new?template=bug_report.yml) · [Request a feature](https://github.com/czayas-0314/Badger-Downloads/issues/new?template=feature_request.yml) · [Search existing issues](https://github.com/czayas-0314/Badger-Downloads/issues)

Badger Downloads is the public home for installers, release notes, and feedback for Badger Hub, Meerkat Envelope, and Cappy Comm. Application source is maintained in private repositories. Downloading and using the apps does not require a GitHub account. Submitting an issue or adding a reaction requires a GitHub account.

## Before reporting

Read the [Hub installation and user guide](badger-hub.md), check the release notes for your app and platform, and search for an existing report. Add a reaction to an existing request if it matches your need. If you have new reproduction details, add them to the existing report after removing private information.

Use the bug form for errors, failed installations or updates, and unexpected behavior. Include the affected app version, operating system and version, processor type, steps to reproduce, expected behavior, and actual behavior. Include Hub's version when the problem involves Hub. Use fictional sample data.

Use the feature form to explain the task you are trying to complete, the obstacle, and the change you propose. Describe any workaround you have tried. One problem or request per issue makes review and follow-up easier.

Hub's feedback links open the public GitHub form in your browser. They pre-fill only the app, a valid app version when known, Hub version, operating system family, and processor type. They do not submit an issue, attach files, or include logs, local file paths, account details, or credentials. Review the form before submitting.

## Keep private information out

Issues, comments, and attachments in this repository are public. Do not post passwords, sign-in codes, tokens, credentials, customer data, real names or addresses, account identifiers, private documents, or unredacted screenshots and logs. Replace personal details with fictional examples. Remove names and local paths from error text before posting.

For a sensitive report, ask the maintainer for a private reporting route without including sensitive details in the public request. Do not assume an issue or attachment is private.

## How reports are reviewed

New reports wait for maintainer review. The maintainer uses the app field and the `bug` or `enhancement` label to identify the subject, then applies a status as the work progresses:

| Status | Meaning |
| --- | --- |
| `needs-info` | The maintainer needs specific details to understand or reproduce the problem. |
| `accepted` | The report is understood and suitable for further work. This does not promise delivery or a date. |
| `in-progress` | Implementation or verification is under way. |
| `released` | A public release contains the change. The issue should link to that app's release notes and version. |

Status labels describe the current state; replace an earlier status when the state changes. Duplicates can be closed with a link to the original. Out-of-scope requests can be closed with a short explanation. A source change or local test alone does not qualify as `released`. Mac and Windows release availability can differ by app; check the linked platform release notes.

There is no guaranteed response or release schedule. Keep follow-ups focused on information that helps reproduce the problem or assess the request.

## Contributions and application source

Bug reports, reproducible examples with fictional data, feature requests, and corrections to the public documentation are welcome here. A public documentation pull request must contain only material intended for public distribution.

Application code changes require a separate private-source workflow and the repository owner's approval for access. Opening a public issue does not grant access or authorize copying private code, source archives, credentials, build folders, or internal documents into this repository. Coordinate proposed code work with the maintainer before sharing an implementation.
